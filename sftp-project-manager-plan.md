# План разработки portable SFTP-менеджера для программистов

Дата: 5 октября 2026 года.

## 1. Задание будущему агенту

Разработать настольное приложение: пользователь выбирает локальный проект, добавляет несколько SSH/SFTP-подключений, задаёт соответствие локальных и удалённых директорий и вручную загружает или скачивает файлы.

Главный сценарий — заменить востребованную часть Deployment из PhpStorm при переходе на другой редактор. Приложение не должно зависеть от PHP, Bitrix или конкретной IDE. Встроенный ИИ не требуется; ИИ используется для разработки проекта.

Пользователь — PHP/Vue-разработчик, изучающий Go. Реализация должна быть понятной, модульной и без избыточной инфраструктуры. Не создавать микросервисы, облачный backend, регистрацию или платёжную систему.

Этот документ — план, а не подтверждение готовности реализации. Чекбоксы отмечать только по фактическим результатам. Не выдавать сборку или тестирование под Windows за выполненные, если проверка была только в Linux.

## 2. Подтверждённые требования

- Локальная папка является корнем проекта.
- Поле «Локальная папка проекта» поддерживает выбор через стандартный диалог Windows, чтобы не вводить путь вручную.
- Несколько подключений на проект.
- Импорт именованных подключений из пользовательского `.ssh/config`.
- Импорт проектов и SFTP/SSH deployment-конфигураций из выбранной папки с проектами PhpStorm: найти проекты с `.idea` и поддерживаемыми SSH/SFTP-серверами, перенести локальные корни, подключения и доступные маппинги.
- Поддержка и `ProxyJump`, и `ProxyCommand` из доверенного SSH-конфига для подключения через промежуточные узлы. Оба способа входят в MVP.
- Настраиваемый маппинг локальных и удалённых директорий.
- Загрузка и скачивание файлов и папок.
- Portable-поставка по модели «распаковать архив и запустить .exe».
- Запуск на рабочем Windows-ноутбуке без прав администратора.
- Для конечного пользователя не требуется установка Go, Node.js или средств разработки.
- Работа локально, без отправки файлов и ключей во внешние сервисы.

## 3. Предлагаемые решения и открытые вопросы

Предложения ниже не выдавать за уже утверждённые пользователем детали.

| Вопрос | Рабочее предположение |
| --- | --- |
| Первая платформа | Windows x64; версию Windows уточнить до окончательного выбора runtime |
| UI | Go + Wails + Vue 3 + TypeScript |
| Язык интерфейса | Русский для первой версии |
| SSH | Системный OpenSSH через отдельный процесс; проверить наличие на целевом ноутбуке |
| Первая авторизация | Ключ или доступный SSH-agent; пароль и MFA уточнить |
| Автозагрузка при сохранении | Не входит в первый MVP |
| Интеграция с IDE | После MVP; точный продукт OpenIDE и его возможности неизвестны |
| Хранение настроек | JSON с версией схемы в `data` рядом с exe |
| Секреты | Не сохранять пароли и passphrase в JSON; ключи не копировать |
| Импорт PhpStorm | Разобрать проектные deployment-настройки из `.idea`; глобальные настройки и секреты не импортировать автоматически |

Сначала уточнить только вопросы, меняющие ближайший этап: версия/архитектура Windows, наличие OpenSSH и способ авторизации. Необходимость поддержки ProxyJump и ProxyCommand подтверждена пользователем; конкретные конфигурации можно уточнить для интеграционных проверок. Остальные решения можно принимать по этому плану. Отсутствие доступа к рабочему ноутбуку не мешает писать ядро, но оставляет проверку целевой среды незавершённой.

### Импорт проектов PhpStorm

Пользователь выбирает родительскую папку с проектами PhpStorm. Импортёр рекурсивно ищет корни проектов по `.idea`, разбирает поддерживаемые project-level deployment XML и предлагает импортировать проекты, в которых есть SFTP/SSH подключения. Для каждого проекта показать найденные серверы и маппинги до сохранения; позволить пропустить проект и разрешить конфликты с уже существующими именами/путями. Импорт не запускает SSH и не меняет исходные проекты.

JetBrains хранит настройки проекта в XML-файлах `.idea`, но часть deployment/SSH настроек может быть IDE-level, а секреты могут находиться вне проекта. Поэтому импортировать только явно найденные поддерживаемые значения, не искать секреты в хранилище IDE и не переносить пароли/passphrase. Предпочитать SSH alias из `.ssh/config`; если конфигурация содержит прямые host/user/port/key параметры, перенести только поддерживаемые поля и показать пользователю результат. Неподдерживаемые типы, отсутствующие файлы и неоднозначные/недоступные mappings отобразить как предупреждения, а не молча угадывать.

Перед реализацией зафиксировать реальные варианты XML на нескольких версиях PhpStorm и проверить, какие поля относятся к `.idea` и какие — к пользовательской конфигурации IDE. Основная справка подтверждает хранение настроек проекта в `.idea` и отдельно описывает глобальные deployment-серверы: [project settings](https://www.jetbrains.com/help/phpstorm/creating-local-server-configuration.html), [deployment export/import](https://www.jetbrains.com/help/phpstorm/export-import-deployment-settings.html).

## 4. Границы MVP

### Входит

- Создание, редактирование и удаление профиля проекта без удаления файлов проекта.
- Ручное добавление подключения и выбор SSH-алиаса.
- Несколько маппингов для каждого подключения.
- Проверка подключения с понятной диагностикой.
- Локальное и удалённое дерево с загрузкой каталогов при раскрытии.
- Выбор нескольких файлов и рекурсивная передача папки.
- Исключения, видимые и редактируемые пользователем.
- Предпросмотр направления, сервера, путей и перезаписей до начала операции.
- Очередь, прогресс, отмена и ручной повтор неудачных задач.
- Подтверждение перезаписи, журнал ошибок и результатов.
- Сохранение настроек между запусками.

### Не входит

- Двусторонняя синхронизация, автоматическое удаление и зеркалирование.
- Автозагрузка по событиям файловой системы.
- Встроенный редактор, терминал и автоматическое слияние конфликтов.
- FTP, WebDAV, S3, удалённый sudo.
- Автоматическое обновление приложения и runtime.
- Полная замена всех возможностей PhpStorm Deployment.
- Поддержка всех ОС и всех способов SSH-аутентификации одновременно.

## 5. Portable и отсутствие прав администратора

1. Приложение запускается с правами текущего пользователя, без запроса UAC, установки служб, драйверов и системных переменных.
2. Архив распаковывается в папку, доступную пользователю для записи. Не использовать Program Files как обязательное расположение.
3. Настройки, журнал, временные данные приложения и WebView2 user data размещаются в `data` относительно расположения exe, а не текущей рабочей директории процесса.
4. Если папка недоступна для записи, показать понятную ошибку и предложить перенести приложение. Не делать незаметный переход к другому каталогу настроек.
5. Существующий `.ssh/config` читать без изменения. Пользовательские ключи остаются на исходных путях. Подтверждённое добавление ключа сервера хранить по явно выбранной политике known_hosts.
6. Отдельно проверить работу без установленного Go/Node.js и запуск из пути с пробелами и кириллицей.
7. Portable не отменяет AppLocker/WDAC, антивирусные ограничения или ограничения исходящих SSH-соединений. Не пытаться обходить корпоративные политики.

### WebView2

Wails под Windows требует WebView2 Runtime. Предусмотреть обычный архив, использующий установленный runtime, и проверить возможность автономного архива с Fixed Version Runtime рядом с приложением.

Не обещать универсальный запуск автономной сборки без проверки конкретной версии Windows и runtime: у Fixed Version бывают дополнительные требования к размещению и разрешениям. Если вариант требует действий администратора, он не удовлетворяет требованиям пользователя. Проверить официальную документацию выбранных версий и реальный запуск обычным пользователем.

### OpenSSH

Установка системного OpenSSH может требовать админских прав, поэтому нельзя делать её обязательным шагом для пользователя. На первом этапе определить, доступен ли `ssh.exe`. Если нет, оценить поставку разрешённого portable SSH-клиента с лицензиями либо native Go transport. Выбор описать отдельно; native transport не считать автоматически совместимым со всеми директивами OpenSSH.

## 6. Архитектура

Предлагаемые компоненты:

| Компонент | Ответственность |
| --- | --- |
| UI на Vue | Проекты, подключения, деревья, диалоги, очередь |
| Application service | Пользовательские действия и события прогресса |
| Project/config | Модель проектов, версия схемы, сохранение |
| SSH discovery | Импорт алиасов и отображение эффективных параметров |
| Transport | SSH-процесс и SFTP-клиент; единый интерфейс операций |
| Mapping | Расчёт локального/удалённого пути и проверка границ |
| Transfer planner | Обход выбранных каталогов, исключения, список операций |
| Transfer queue | Выполнение, отмена, прогресс и результаты |

Ядро Go не зависит от Vue и Wails. UI получает ограниченный набор методов и события, а не прямой доступ к произвольному выполнению команд. Это позволит позже добавить CLI для вызова из редактора.

### SSH и SFTP

- Рассмотреть `pkg/sftp` поверх stdin/stdout системного OpenSSH, запускающего подсистему SFTP.
- Передавать массив аргументов без shell. Под Windows использовать `CreateProcess` с системным экранированием аргументов, приостановленным запуском и назначением Job Object до возобновления; `exec.CommandContext` сам по себе не гарантирует завершение дочерних процессов.
- Разделять бинарный SFTP stdout и диагностический stderr.
- Поддержать ProxyJump (включая цепочку узлов) и ProxyCommand через системный OpenSSH с тем же доверенным конфигом, который выбран для подключения. Не переписывать эти директивы и не подменять их значением `none` в готовом MVP. ProxyCommand исполняется средствами OpenSSH; приложение не конструирует собственную shell-команду из полей формы.
- Обеспечить завершение процесса и освобождение ресурсов при отмене/закрытии, включая дерево дочерних процессов ProxyJump и ProxyCommand под Windows. Снятие текущего ограничения требует реализации и проверки управления этим деревом; одного удаления аргументов `none` недостаточно.
- Для первого вертикального среза допустим неинтерактивный режим ключ/агент. Он должен быстро и понятно завершаться при необходимости ввода пароля, а не зависать.
- Интерактивные пароли, passphrase и MFA — отдельный сценарий. Не подменять их записью пароля в аргументы процесса или конфиг.
- Проверять ключ сервера. Не использовать глобальное отключение проверки host key. Новый ключ требует явного подтверждения отпечатка, изменившийся — остановки подключения.

### Импорт `.ssh/config`

- Значение по умолчанию: `%USERPROFILE%\.ssh\config`, с возможностью выбрать другой файл.
- Показывать конкретные положительные алиасы из `Host`; маски и отрицательные шаблоны не считать готовыми серверами.
- Обработать `Include` с ограничением глубины/защитой от циклов; неподдерживаемые случаи показывать явно.
- Разрешить ручной ввод алиаса, которого нет в списке.
- Эффективные настройки получать через `ssh -G`, подключение выполнять с тем же конфигом.
- Учитывать, что конфиг может содержать исполняемые директивы вроде `Match exec` и `ProxyCommand`: импорт/оценку стороннего конфига не считать пассивным чтением текста. Не запускать такие файлы автоматически при просмотре папок.
- Не копировать и не переписывать пользовательский SSH-конфиг ради хранения маппингов.

## 7. Модель данных

- `Project`: id, имя, абсолютный localRoot, подключения.
- `Connection`: id, имя, абсолютный POSIX rootPath для просмотра, режим `ssh_alias` или `manual`, alias/configPath либо host/user/port/identityFile, mappings, excludes.
- `Mapping`: id, localPath относительно project root, deploymentPath относительно rootPath сервера (`.` означает сам корень).
- `TransferTask`: id, снимок параметров подключения и маппинга, направление, source, destination, размер, статус, прогресс, ошибка.

Изменение выбранного подключения в UI не должно менять адрес назначения уже поставленных в очередь задач. Секреты в конфиг, задания и логи не включать.

Пример предлагаемого конфига, не контракт публичного API:

```json
{
  "schemaVersion": 3,
  "projects": [{
    "id": "example-project",
    "name": "My app",
    "localRoot": "C:\\Projects\\my-app",
    "connections": [{
      "id": "dev",
      "name": "Development",
      "rootPath": "/srv/app",
      "connection": {"mode": "ssh_alias", "alias": "work-dev"},
      "mappings": [{"id": "root", "localPath": ".", "deploymentPath": "."}],
      "excludes": [".git/**", "node_modules/**"]
    }]
  }]
}
```

Запись настроек — через временный файл и замену, с сохранением предыдущей валидной версии. Не перезаписывать повреждённый конфиг пустым без уведомления.

## 8. Правила маппинга и передачи

1. Локальные пути обрабатывать средствами ОС, удалённые — POSIX-правилами; не применять Windows filepath.Join к remote path.
2. Разрешать только локальные пути внутри корня проекта; учитывать границы сегментов, `..`, регистр и симлинки/junctions, а не проверять строковый префикс.
3. Для первой версии запрещать пересекающиеся local roots и пересекающиеся remote roots внутри одного подключения. Это делает обратное отображение однозначным. Позже можно добавить явно описанную поддержку вложенных маппингов.
4. Файл вне маппинга не отправлять «по догадке» — показать причину.
5. Симлинки/junctions в MVP отображать, но не обходить и не передавать; проверять также промежуточные сегменты пути назначения. Уточнить поддержку серверных symlink-root отдельно.
6. Для скачивания обрабатывать недопустимые Windows-имена и коллизии регистра явной ошибкой; не переименовывать молча.
7. Синтаксис исключений определить и описать. Не обещать совместимость с `.gitignore`, если она не реализована. `.env` не отправлять массовой операцией без явного включения пользователем.
8. Передачу планировать до выполнения. Показывать сервер, направление, целевые пути, число файлов и известный объём.
9. Совпадение размера и mtime не называть доказательством одинакового содержимого. Полный diff/hashing не обязателен для MVP.
10. При существующем целевом файле предложить перезапись, пропуск или отмену; конфликт «файл вместо каталога» считать отдельной ошибкой.
11. Писать во временный файл в целевом каталоге и заменять после успешной передачи. Проверять поддержку rename/replace; не удалять оригинал как скрытый fallback. Ограничения атомарности и сохранения прав документировать.
12. Проверять доступные метаданные назначения повторно перед заменой, чтобы обнаружить часть конкурентных изменений. Не обещать полной защиты от гонок без серверной поддержки.
13. Ограничить параллелизм; начать с одного активного файла на подключение. Отмена должна прекращать I/O, а временные файлы убираться по возможности с явным статусом при неудаче.
14. Ошибка одного файла не должна скрывать результаты остальных. Повторять только явно выбранные неудачные задачи; не выполнять скрытый повтор перезаписи после неопределённого результата.

## 9. Интерфейс

Уточнение пользователя от 6 октября 2026: первый запуск предлагает создать проект только с названием и локальной папкой, сохранив его в JSON. Рабочее окно организовано как в PhpStorm: полный локальный проект слева, изначально пустая область сервера справа. SSH/SFTP-серверы добавляются и выбираются в отдельном окне настроек; сервер по умолчанию — первый созданный, с возможностью изменить выбор. После сохранения серверов правая панель показывает дерево от настроенной удалённой папки; SSH запускается явно пользователем. Полный контракт: [docs/ide-workspace.md](docs/ide-workspace.md).

- Слева — проекты, сверху — выбранное подключение и заметное имя сервера.
- Слева — дерево полного локального проекта, справа — дерево выбранного сервера от корня удалённой папки; текущие пути и маппинг видимы. Локальное дерево доступно и без серверов.
- Действия подписать однозначно: «Загрузить на сервер», «Скачать на компьютер».
- Внизу — очередь: файл, направление, сервер, прогресс, статус, ошибка.
- Отдельные формы: проект, подключение, маппинги, исключения.
- Рядом с полем «Локальная папка проекта» — кнопка «Выбрать папку…», открывающая стандартный диалог выбора каталога Windows. После выбора поле заполняется абсолютным путём; ручное редактирование сохраняется. При отмене диалога текущее значение не меняется. Выбранная папка проходит ту же валидацию корня проекта, включая проверку ссылок/junctions. Выбор папки не сохраняет профиль и не запускает подключение автоматически.
- Состояния: подключение, пустой каталог, нет прав, сеть недоступна, отменено.
- До передачи показывать сервер и направление; подтверждать перезаписи в одном понятном диалоге.
- Не включать автоподключение и передачу при старте приложения.

### Этап 0. Проверка возможности запуска

- [ ] Проверить актуальные версии Go/Wails и совместимость с целевой Windows; зафиксировать версии.

## 11. Проверки, необходимые для доверия к передаче файлов

### Автоматические

- Маппинг в обе стороны, корень проекта, пробелы/кириллица, `..`, пересечения, выход через ссылки.
- Исключения и отсутствие неявного переноса исключённых файлов.
- Фиксация подключения в задаче при переключении UI.
- Перезапись/пропуск, отмена, очистка временных файлов, ошибки rename и недостатка прав.
- Интеграция с тестовым SSH/SFTP-сервером: листинг, бинарный round trip, обрыв соединения, неизвестный/изменённый host key.
- Отдельно проверить ProxyJump и ProxyCommand в изолированной среде: листинг, бинарный round trip, ошибки промежуточного узла, отмену и закрытие приложения без оставшихся дочерних процессов. Проверка ключей сервера остаётся обязательной для SSH-узлов цепочки; для произвольного proxy-клиента проверку промежуточного узла обеспечивает его доверенная конфигурация.
- Для Windows отдельно: поведение путей, регистр, зарезервированные имена и завершение процессов.

Тестовый сервер использовать в изолированной среде разработки; Docker не является зависимостью приложения на рабочем ноутбуке. Не проверять разрушительные сценарии на рабочих серверах.

### Ручные smoke tests portable-сборки

- Запуск обычным пользователем без установленного Go/Node.js.
- Запуск из папки с пробелами и кириллицей.
- Перезапуск и сохранность проектов/маппингов.
- Проверка на установленном WebView2; отдельно автономная поставка, если реализована.
- Нет OpenSSH/runtime: понятная диагностика без требования «запустить от администратора».
- Передача папки с вложениями, отмена большого файла, повтор после обрыва.
- Закрытие приложения во время передачи не оставляет зависший SSH-процесс.

## 14. Оптимизация контекста и передача работы агентам

- Оптимизировать контекст на протяжении разработки: не полагаться на сохранность всей переписки и не перечитывать весь проект при каждом продолжении.
- Начинать продолжение с `docs/agent-context.md`: текущий этап, подтверждённые факты, открытые вопросы и ближайшие действия. Нужные разделы этого плана и исходники читать по текущей задаче.
- Обновлять файл состояния после завершения этапа, существенного решения или проверки, а также перед передачей работы и сжатием контекста. Заменять устаревшие сведения, а не накапливать стенограмму.
- Разделять реализованное, проверенное и предполагаемое. Для проверок записывать команду, результат, среду и ограничения; чекбоксы этапов отмечать только по фактическим результатам.
- При необходимости создавать дополнительные тематические `.md` в `docs/` для решений, проверок и отдельных этапов; ссылки на них держать в файле состояния. Не дублировать один и тот же план в нескольких файлах.
- Искать нужные файлы и символы точечно; ограничивать вывод команд релевантными строками. Не помещать в контекст зависимости, сгенерированные файлы, бинарники и полные журналы без необходимости.
- Не записывать в документы ключи, пароли, passphrase, содержимое пользовательского SSH-конфига и другие секреты.
- Если используется несколько агентов, передавать каждому конкретную задачу, необходимые пути, ограничения и критерии проверки. Эти пометки сами по себе не требуют создания дополнительных агентов.
- По указанию пользователя Superpowers не использовать.
