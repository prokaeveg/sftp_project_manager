# ProxyJump и ProxyCommand

Подключения через промежуточные узлы используют режим SSH-алиаса и исходный доверенный конфиг. Отдельных полей для сборки shell-команды в приложении нет. Ручной режим host/user/port использует пустой SSH-конфиг и прямое подключение.

## Настройки узлов

OpenSSH не переносит параметры конечного сервера на jump-узлы. В конфиге необходимо задать их ключи/агент и проверенный `known_hosts`, строгую проверку ключей и неинтерактивный режим. Поле known_hosts в форме действует на конечный сервер; jump-узлы читают собственные настройки из конфига.

Пример структуры (адреса и имена заменить своими):

```sshconfig
Host *
    BatchMode yes
    StrictHostKeyChecking yes
    ForwardAgent no
    ControlMaster no
    ControlPath none
    PermitLocalCommand no
    ForkAfterAuthentication no

Host jump1
    HostName jump1.example.com
    User developer
    IdentityFile ~/.ssh/id_ed25519

Host jump2
    HostName jump2.internal
    User developer
    IdentityFile ~/.ssh/id_ed25519

Host app-jump
    HostName app.internal
    User developer
    ProxyJump jump1,jump2

Host app-command
    HostName app.internal
    User developer
    ProxyCommand ssh.exe -F "C:/Users/you/.ssh/config" -W %h:%p jump1
```

Для ProxyCommand путь `-F` должен указывать на тот же выбранный конфиг, если команда использует SSH-алиас из него. Произвольная команда может быть другим TCP-прокси; проверку самого такого промежуточного сервиса обеспечивает его доверенная конфигурация. Конечный SSH-сервер всегда проверяется приложением через `StrictHostKeyChecking=yes`. Политику SSH-процессов внутри произвольного ProxyCommand задаёт сам конфиг/команда.

Не включать одновременно ProxyJump и ProxyCommand для одного назначения: OpenSSH использует первый заданный вариант. Настройки первой найденной директивы имеют приоритет, поэтому общие ограничения в примере расположены в начале.

Проверенный Windows OpenSSH 9.5 некорректно передаёт путь `-F` с пробелами во внутреннюю команду ProxyJump. Для ProxyJump используйте конфиг по пути без пробелов. Это ограничение системного SSH; приложение не переписывает конфиг. ProxyCommand с явно заключёнными в кавычки путями программы и конфига проверен интеграционно.

## Жизненный цикл

Под Windows SSH запускается приостановленным и помещается в Job Object до начала выполнения. Job включает дочерние команды из ProxyJump, ProxyCommand и Match exec. Отмена, закрытие сессии, ошибка подключения и закрытие приложения завершают созданное дерево и освобождают дескрипторы. Приложение не управляет SSH-сессиями, которые были запущены независимо от него; для jump-узлов в конфиге нужно отключить их переиспользование через ControlMaster/ControlPath.

SFTP stdout остаётся бинарным потоком; stderr читается отдельно с ограничением размера. Команды прокси и необработанный stderr не записываются в журнал и не показываются как ошибка. Для непроверенной платформы поддержка алиасных прокси не включается автоматически.

Алиасы ограничиваются буквами, цифрами, точкой, подчёркиванием и дефисом: OpenSSH может подставлять их в команды без shell-экранирования. Параметры HostName и текст ProxyCommand из доверенного конфига остаются ответственностью владельца конфига.

## Навигация

`internal/transport` — SSH и управляемые процессы; `proxy_integration_test.go` — изолированные промежуточные SSH-узлы и бинарная передача; `internal/application/proxy_shutdown_windows_test.go` — закрытие сервиса во время proxy handshake. Результаты и фактические ограничения — в `verification.md`.

Семантика промежуточных узлов, конкуренции ProxyJump/ProxyCommand и подстановки токенов сверена с [руководством OpenSSH](https://man.openbsd.org/ssh_config).
